# Broker-connected demo execution

Implemented 4 October 2026. This extends the existing trading workstation with OANDA practice and Alpaca paper adapters, durable order intents and append-only broker observations. It does not certify full project completion or autonomous broker strategy execution.

## Available workflow

Open **Paper trading → Broker-connected demo trading**, choose a broker and check its account and current positions. The account check reads the actual broker account and exposure, including positions created outside this workstation. OANDA balances remain in the account's home currency; pricing retains broker quote-to-home conversion factors. Alpaca reports its actual cash, equity and buying power. Market-data access and trading-account access are separate checks.

Enable demo orders, enter an instrument, side, quantity, order type, duration and reason, then submit. Optional broker-held stop loss and take profit are attached to a supported market/limit entry. This route uses OANDA currency units and Alpaca whole shares. The broker's instrument increments, minimum/maximum quantity, buying power and account restrictions remain authoritative. The owner's current instruction is no additional exposure, position, per-trade or daily-loss caps; the policy explicitly records that choice. No policy is seeded by installation.

Each owner order creates an immutable intent and stable client order ID before network submission. A committed submission marker prevents automatic resubmission after interruption. Repeated request IDs return the original intent; changing a request with the same ID is rejected. A lost response, unknown status, mismatched order or decreasing cumulative fill records reconciliation-required status. A broker not-found response after uncertain submission does not permit another submission. The browser can recover an unanswered request with its original ID.

The independent broker worker resumes prepared intents and polls unresolved/pending broker orders. Repeated unchanged observations do not append duplicate history. Cancellation is a request, not a presumed completed cancellation: partial or final fills are retained. Terminal intents cannot be reactivated or returned to prepared state. The worker continues tracking filled entries, broker-held protection, partial exits and final closure. A zero attributed balance remains unresolved until entry and protective orders are terminal, so a late protective-order race stays visible.

Stopping new demo orders revokes future submission authority and leaves existing orders visible for reconciliation/cancellation. Changed credentials invalidate new submission authority. Read-only reconciliation and cancellation can use rotated demo credentials only after verifying the same broker account fingerprint. Real-money connection configurations fail before any execution request. Broker hosts are fixed, redirects are rejected and credential/provider error bodies are not returned.

## Attributed broker positions and closes

Filled entry intents have an independent position cursor. The owner can **Check position**, inspect the **Broker position journal**, and close an explicit quantity against that entry. Close requests have immutable authority, stable IDs, committed pre-network markers and append-only observations. A PostgreSQL lock spans the durable commits and broker calls, preventing competing API/worker instances from issuing the same close. Once a close submission marker exists, recovery only reads broker evidence; a missing order after an uncertain request never permits another submission. Partial fills update the journal while the close remains pending.

OANDA positions use the actual entry's trade IDs and verified closing transactions. Manual exits target that trade, preserving unrelated trades. Realized P&L and financing remain separate amounts in the account's home currency; entry/exit notionals remain in the instrument's quote currency. Attached protective fills are attributed from closing transactions. Alpaca uses actual FILL activities for entries, protective legs and manual closes, with identity and cumulative-quantity checks across bounded pagination. Its displayed P&L is virtual gross attribution at this entry's average acquisition cost, excluding fees, dividends and broker tax-lot differences.

Alpaca manual closes cancel this entry's protective legs once and wait for terminal confirmation before placing a reducing order. Lost cancellation responses recover by observation without repeating cancellation. A protective fill during preparation reduces or fulfils the remaining requested close. Partial manual closes leave any residual shares without the cancelled attached protection; the close form explains this consequence. OANDA partial trade closes retain the remaining trade's broker protection.

Each observation records actual broker holdings for the matching instrument and side. A shortfall blocks a new attributed close; excess holdings can include other platform entries or external positions and are preserved. This is a per-entry coverage check, not certification that the entire account's external activity has been attributed. Excess protective fills, missing execution activities, changed lineage and backwards quantities remain reconciliation failures rather than inferred exits.

## Exact native demo setup review

Under the broker controls, **Review a demo trade setup** accepts a saved executable breakout strategy version, matching OANDA FX or Alpaca stock/ETF instrument, explicit currency units or whole shares, and the selected cloud/local AI connection. The screen defaults to a configured connection. **Check setup evidence** evaluates actual closed-bar rules and reads broker account, holdings, instrument increments and bid/ask evidence. It places no order and invokes no model. Quotes must be positive, uncrossed, tradable and no more than 60 seconds old. Alpaca checks its actual paper clock and requires positive displayed quote sizes; its selected IEX/SIP feed remains explicit. Stops round down to the broker increment, targets round up, and the proposed quantity stays exactly as requested. Simulator capital/risk parameters do not become broker caps under the owner's no-limits policy.

**Request Tauric setup review** recaptures this evidence, requires a valid entry, and queues a separate immutable native job. The worker verifies the strategy, snapshot, enabled policy, account fingerprint, connection revision, model fingerprint and expiry before starting the pinned native runtime. A changed or expired admission fails without starting a model process. Reusing a request ID returns its original run, including a failed run; changed inputs with the same ID fail. A lost browser response can recover this same job without another invocation. Job contexts cannot mix this review with qualification, autonomous paper, scanners, chat or portfolio research.

The pinned native graph keeps its original daily reports and rating. A separate deep-model structured verdict binds the setup ID, exact strategy version, evidence checksum, instrument, provider, buy side and quantity. Original stock/ETF ratings other than BUY reject this long setup without another review call. Forex's original REVIEW status remains REVIEW; the FX extension assesses the exact pair/strategy setup separately and must discuss the supplied two-currency evidence and declared gaps. Invalid bindings, oversized inputs, stale evidence or provider failures produce an incomplete/rejected setup assessment, without a retry. This extension cannot qualify a strategy, mint OpenClaw permission or grant execution authority. Its result cannot substitute for ordinary paper-entry research or paper governance.

Saved native reviews remain readable after reload, including expired evidence and the untouched original report. Native review itself grants no permission. The separate bound OpenClaw path below can authorize one exact demo entry; scheduled discovery and connected fill validation remain pending.

## Bound OpenClaw demo entry reviews

A current successful native setup approval can be submitted to **OpenClaw demo entry approval**. The owner selects the cloud/local connection and either review only or **Submit this exact demo entry automatically if allowed**. Review only requires a separate submit action after an allow. The automatic option covers that single frozen setup; it does not enable discovery or scheduling of future trades. The original native stock rating or Forex REVIEW report remains unchanged. Forex artifacts retain their explicit daily-extension runtime and frozen pair evidence.

Separate immutable broker review jobs and decisions bind the native job/artifact, evidence checksum, strategy version, demo policy, provider, instrument, exact quantity, stop/target, account fingerprint and connection revision. OpenClaw has an isolated broker governor per configured model profile and a single read-only bound-context tool. It has no order or sizing tool. Its allow/reject/defer response must match every binding and prove the active context was retrieved. Paper simulator capital/risk parameters are not broker caps under the owner's no-limits policy.

Paper and broker governance share one fair leased queue and the existing bounded review capacity. A timed-out/interrupted review does not automatically call the model again. Optional owner-wide AI admission allowances include these jobs; this is an AI resource allowance, separate from trade limits. The Gateway advertises the broker-review capability only after loading the new project plugin/configuration. Until then broker reviews are refused.

An allow can be consumed by one durable broker intent, whether delivery is requested automatically or the owner submits it. The decision link is unique and immutable in PostgreSQL. A stable broker client ID and committed submission marker precede the broker mutation. Worker restart after approval can deliver the unfinished entry; restart after uncertain submission only reconciles. A lost response or broker not-found result never permits another order. Repeated consume requests return the existing intent even with another request ID.

Before submission, the platform rechecks the original native approval, live policy/connection/model identity, exact closed-bar signal, bid/ask freshness and trading availability, instrument constraints, current holdings/cash, and stop/target bounds. Changed facts or expired approval create a durable rejected intent without a broker order. A final guard runs immediately before the actual mutating HTTP request. Owner/order locking follows a consistent order and permits foreign-key receipt checks, including competing workers. Existing order/position controls continue to handle actual fills, protection and attributed closes.

Offline integration evidence covers Alpaca exact-entry fills and attributed close with external shares preserved; OANDA bound review with unchanged Forex REVIEW rating, GBP home-currency facts, currency units and FOK protection prices; wrong/stale/unread results; immutable SQL authority; ownership; competing deliveries; expired leases; pause/config/account changes; and uncertain broker responses without resubmission.
