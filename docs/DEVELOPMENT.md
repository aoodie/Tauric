# Development workstation

This profile previews the workstation, public spot charts and optional native analysis worker. Cloud and external-local AI configuration is deferred until the owner supplies connection details in Settings → AI connections. There are no broker adapters or execution workers. See [model connections](MODEL_CONNECTIONS.md).

## Start and create the owner

Follow the three commands in the root README. Python 3 is needed only to generate the private `.env`; the application builds inside Docker. Docker image bases are pinned to multi-architecture digests and frontend/backend dependencies are locked. Local validation used Linux arm64 containers through Docker Desktop on macOS. A clean Linux host and Linux amd64 installation are not yet verified.

Defaults are web port 8080 and PostgreSQL port 54330, both loopback-only. If occupied, edit `.env` before starting. A changed web port must also appear in `TAURIC_ALLOWED_ORIGINS`. Never paste secrets into chat, commit `.env`, or share expanded Compose configuration containing credentials.

The owner password is prompted inside the API container. It must be at least 12 characters. Owner creation also creates the initial Trading workspace and records setup. Signed-in password changes are available in Settings → Security and revoke all sessions. Public registration and forgotten-password reset are not implemented. Keep the password securely; owner recovery needs a documented administrative path in a later milestone.

Readiness is at `/health/ready`; process reachability is `/health/live`. Readiness checks migrated storage. The application reports empty/fresh/stale snapshots, worker heartbeat and unconfigured model profiles separately. Worker-ready is not proof of a successful AI run.

## Edit locally

Keep the database container running, then install the locked dependencies:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.lock
npm --prefix frontend ci
```

Run the API and frontend in separate terminals:

```sh
python3 scripts/local.py api
```

```sh
npm --prefix frontend run dev
```

Open `http://127.0.0.1:5173`. Requests are proxied to the local API, using the same development database and owner as the Docker preview. Stop local editing servers when finished. Rebuild Docker to preview updated production assets.

The runtime database role cannot change table definitions, alter history or disable its protections. Migrations use a separate administrator role. The initial migration contains a frozen schema and setting definitions; future changes must be new migrations. Finalized settings, layouts, definitions and audit events reject update/delete/truncate. This protects against application mistakes and ordinary SQL mutation; a database superuser or host administrator can still deliberately remove protections.

## Checks

```sh

.venv/bin/ruff check backend scripts
npm --prefix frontend run build
npm --prefix frontend run format:check
```

Backend tests create and remove disposable PostgreSQL databases; they do not erase the development database. They need the local administrator credentials generated by setup.

When API contracts change:

```sh
cd backend
../.venv/bin/python -m tauric.cli export-openapi --output openapi.json
cd ..
npm --prefix frontend run generate:api
npm --prefix frontend run format
```

Browser checks require Python Playwright and Chromium, with ports 8000 and 5173 free. Create an isolated owner/database with `.venv/bin/python scripts/prepare_browser_test.py`, run `python3 scripts/browser_api.py` and the frontend development server, then `python3 scripts/browser_test.py`. The browser API loads only the ignored temporary test credentials. The suite also briefly stops/restarts the local development database and restarts its Docker API; run it only while this development stack is idle. Always stop both browser-test servers before running `.venv/bin/python scripts/cleanup_browser_test.py`, which removes the disposable database and credentials while retaining screenshots. The private fixture must never be published.

After the 11 browser workflows, `python3 scripts/docker_browser_test.py` verifies built assets, Caddy headers and persisted state through isolated containers on port 8081. Build the development images first. It shares the development database server but connects only to the disposable test database, and removes its temporary containers when finished. Run `scripts/market_browser_test.py` against the same editing servers to check actual public candles and mobile controls (requires outbound Binance access). Run `scripts/owner_settings_browser_test.py` on the editing servers to verify AI connection saves and password changes using the disposable account. It restores that test account’s original password and makes no model calls. Run fixture cleanup afterward. The market checks create an extra temporary workspace but preserve the foundation checks’ saved revisions.

## Current limits

- Layouts save explicitly. Restore/reset append new revisions. Stale writes return a conflict and require reloading current data.
- Panel collapse hides contents while retaining its dock space. Maximize, docking, divider resize, close/restore and narrow-screen selection are available. Separate browser popouts and nested tab groups are not enabled.
- Settings have default/global/user resolution. Interface density, timezone, unsaved-layout confirmation, a reserved concurrency preference and three native debate/tool budgets exist. The native worker currently processes one run at a time; the reserved preference does not change this. Account paper policy revisions and strategy limits work; policy scope inheritance remains later work.
- Resource inspection covers owner, setting, workspace and audit resources. It also covers instruments, market snapshots, analysis jobs and original reports; paper proposal/governance/plan/fill and deployment resources now work.
- Backup restoration, upgrade/rollback, host reboot, a 24-hour soak, disk-growth limits and full server resource measurements remain pending.
- The development API image includes test tools. A production release will separate build/test dependencies, supply private service ingress, HTTPS and backup/recovery procedures.

The model endpoint stays disabled; no keys or models are mounted in this slice. Its tokens are generated in private `.env.openclaw-private.json`, copied privately per service and never printed. These are runtime-contract checks, not proof of an AI model connection. The SDK and dependency graph are locked; update them through compatibility checks, not automatic latest-version upgrades.

The real governance verification helpers require a fresh disposable fixture and the saved external-local model connection. They re-encrypt the saved credential directly into temporary storage. They never seed primary paper settings, print credentials or force approval. By default the preparation helper copies the latest successful current-day real BTC report unchanged; `--source-artifact UUID` selects a specific report. The runner starts separate Gateway/worker services and makes one real review. It verifies either an allowed paper entry/close or planning denial after reject/defer, preserving the model's reason.

To verify a fresh native run through the connected paper workflow:

```sh
.venv/bin/python scripts/prepare_browser_test.py
.venv/bin/python scripts/prepare_real_governance_verification.py --fresh-analysis
.venv/bin/python scripts/real_governance_verification.py
.venv/bin/python scripts/cleanup_browser_test.py
```

Do not reuse a fixture containing previous trades or run another fixture suite concurrently. The fresh mode uses its own native worker/runtime volume, one real native BTC analysis and one real OpenClaw review. All nine original reports and their checksum must pass before review. Only a naturally allowed decision can proceed to planning/filling/closing. The check repeats plan/fill/close request IDs, independently reconstructs cash and realized P&L from linked journal records, rechecks original research, and reads persisted state after an API restart. It does not override a rejected/deferred decision or retry failed model work. A denied review cannot certify the positive workflow.

Model calls may incur provider charges. The fresh native artifact and sanitized results are retained in ignored private `artifacts/real-paper-native-report.json` and `artifacts/real-paper-workflow-results.json`; imported-report mode retains `artifacts/real-governance-results.json`. A completed review also retains the original report, captured review context and paper state in `artifacts/real-paper-workflow-evidence.json`. The runner removes its test containers/runtime volumes. Remove the disposable database/key/owner credentials with the cleanup helper even if verification fails. ## Autonomous paper workflow (0.11.0)

Migration `0015_autonomous_paper` adds durable stages, immutable policies and receipts. It is already followed by the portfolio/research and qualification/market adapter migrations; use the complete current migration chain when upgrading. The default `autonomous_paper` service creates no owner policies and performs only explicitly enabled paper actions. Its native workers require the private OpenClaw routing file for admission checks as well as the chosen model connection.

Enable a scheduled executable deployment first, then save **Autonomous paper execution** settings with a reason. Deployment pause and account halt block entries while permitted attributed exits remain available. Resume waits for a fresh signal; it does not revive blocked attempts or reset daily usage. Disabled authority prevents new writes, while exact committed request retries return their receipts.

Run `python3 scripts/local.py test tests/test_autonomous.py -q` and the strategy rules browser test. For built Linux process recovery, build matching images and run `.venv/bin/python scripts/autonomous_container_test.py`. The driver creates its own `artifacts/autonomy-container.json` fixture and `tauric_autonomy_checks` project, injects synthetic closed candles only into those disposable worker processes, completes explicit synthetic native/review evidence, restarts workers/API, verifies one attributed entry and close, and reconstructs the journal. It never starts an actual AI or broker worker. Cleanup runs on success or failure; logs containing private context stay in ignored files with owner-only access. Run fixture/container suites serially because they use port 8081.

`TAURIC_VERIFICATION_SOURCE` and `TAURIC_VERIFICATION_IMAGE` can select an isolated source/migration snapshot and matching API image during concurrent development; they must describe the same schema. `TAURIC_VERIFICATION_WEB_IMAGE` optionally selects matching built browser assets. These are verification overrides, not production configuration.
